# Nova-Seeds v2.6 Release Candidate Plan (Implementation-Ordered)

## 1) Current repo assessment

### What is present (v2.5 baseline)
- Smart-contract stack exists under `contracts/` with registry, governance, challenge, treasury, workflow adapter, and attestation verifier contracts.
- TypeScript SDK bindings exist under `sdk/` for Lit + TACo and shared EIP-712 helpers.
- Backend exists under `backend/` with FastAPI endpoints, SQL schema bootstrap, and a web3.py indexer.
- Operator dashboard exists under `dashboard/` and reads backend summary metrics.
- Root spec and example JSON payloads are present (`alpha_nova_seeds_v25_spec.md`, `example_*.json`).

### Proven gaps to close for a v2.6 RC
1. **Release engineering:** no CI workflows, no scripted release checklist, no explicit v2.6 acceptance gate.
2. **Provenance:** no signed/hashed release manifest for artifacts, payload examples, ABI snapshots, or migration SQL.
3. **Governance operations:** contract-level governance exists, but no operator runbook or policy evidence schema for challenge outcomes.
4. **Backend proof posture:** current API is a summary endpoint; indexer writes raw chain events but does not normalize to proof-focused read models.
5. **Dashboard proof posture:** dashboard shows activity counters but not evidence lineage/proof completeness.
6. **Testing surface:** no automated test suites observed for contracts, backend, SDK, or dashboard integration.
7. **Repository instructions:** root `AGENTS.md` was absent before this phase; added now to lock doctrine and release discipline.

## 4) Acceptance criteria for v2.6 tag

1. **Proof-first capability:** backend exposes proof completeness endpoints populated from indexed events.
2. **Idempotent indexing:** re-running indexer does not duplicate or corrupt proof projections.
3. **Governance evidence contract:** documented evidence packet schema is versioned and used by examples.
4. **Release provenance:** RC artifact bundle includes deterministic manifest + checksums.
5. **Migration gate:** release notes include explicit migration order (`001_init.sql` baseline + `002_proof_views.sql`), pre-checks, and post-migration verification queries.
6. **Rollback gate:** release notes include tested rollback path (view/table rollback SQL + indexer checkpoint rewind procedure) with owner and decision thresholds.
7. **Operational readiness:** governance challenge runbook exists and references real API/DB objects.
8. **No stack drift:** FastAPI/Postgres backend and Solidity contracts remain the implementation base.
9. **Claim discipline:** docs describe v2.6 as proof hardening RC, not audited/mainnet-final posture.

## 5) Risks / unknowns / assumptions

### Risks
- Event ABI coverage may be incomplete for all governance/proof events needed for robust projections.
- Existing single-pass indexer strategy may struggle with large historical backfills without pagination/batching.
- Dashboard may silently fail on cross-origin/localhost assumptions if deployment topology differs.
- Current schema stores some identifiers as `BYTEA`; endpoint ergonomics may need explicit encoding conventions.

### Unknowns
- Which chain/network(s) are in-scope for v2.6 RC validation.
- Whether governance council seat/slash hooks are fully wired in deployed environments.
- What signing authority model is required for provenance manifest publication (single signer vs multisig).

### Assumptions
- v2.6 remains a release candidate focused on demonstrable proof posture, not narrative expansion.
- Existing v2.5 contract ABIs remain source of truth; v2.6 changes are mostly additive around indexing, views, and ops.
- Team prefers one focused RC PR series rather than a single monolithic merge.
