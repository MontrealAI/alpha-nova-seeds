# Nova-Seeds v2.6 Release Candidate Plan (Implementation-Ordered)

## Section 1: Current repo assessment

### What is already implemented (verified in-repo)
- **Identity → proof → settlement → governance framing is present** in top-level docs and operator dashboard copy.
- **Contracts**: v2.5 Solidity surfaces are present for registry, governance, challenge policy, verifier, treasury, and adapters in `contracts/`.
- **Backend stack is preserved** (`FastAPI + Postgres`) with v2.6-hardening endpoints and migration path:
  - readiness/health and proof/governance metrics in `backend/app/main.py`,
  - deterministic/reorg-safe cursored indexing in `backend/app/indexer.py`,
  - ordered SQL migrations (`001_init.sql`, `002_v26_hardening.sql`) in `backend/migrations/`.
- **Release engineering baseline exists**:
  - CI workflow at `.github/workflows/ci.yml`,
  - release provenance workflow at `.github/workflows/release-provenance.yml`,
  - deterministic manifest generator at `scripts/release/generate_provenance_manifest.py`,
  - release verification guide at `docs/verify-release.md`.
- **Proof documentation and schemas exist**:
  - threshold/decryption schemas in `schemas/v2.6/`,
  - lifecycle/trust/threat docs in `docs/`.
- **Dashboard exists** with proof/governance/provenance views and snapshot export in `dashboard/`.
- **Backend tests exist** for contract surfaces, schema validation, migration/indexer regressions, and provenance workflow invariants in `backend/tests/`.

### Gaps that are still missing for a stronger v2.6 RC gate
1. **Release artifact coverage is incomplete in manifest inputs**
   - `scripts/release/generate_provenance_manifest.py` still targets `example_*_v25.json` and does not include newer v2.6 example payloads and release checklist assets.
2. **No deterministic machine-check for operator release checklist**
   - `release/v2.6/checklist.md` is human-readable but not enforced by CI (no script validating required sections and file presence).
3. **No explicit migration rollback exercise test**
   - rollback notes exist, but there is no automated test that creates v2.6 objects then verifies clean rollback semantics.
4. **Governance evidence packet contract is document-shaped, not schema-enforced**
   - `docs/proof-docket-template/` provides templates, but there is no versioned JSON schema for adjudication packets with backend/dashboard references.
5. **Dashboard has no automated verification**
   - no basic JS smoke test or snapshot contract check for API shape compatibility.
6. **Backend proof API is summary-level only**
   - `/proof/summary` exists, but there is no seed-scoped proof detail endpoint for operator triage (`/proof/seeds/{seed_id}` style surface).
7. **RC migration/backfill runbooks are spread across docs**
   - there is no single operator runbook that sequences migration, backfill, health/proof checks, and rollback decision points in one place.

## Section 4: Acceptance criteria for v2.6 tag

1. **Proof-first scope remains explicit**: release notes and README describe v2.6 as RC hardening, not audited final deployment.
2. **Constitutional ordering is preserved** in docs/comments where sequencing is mentioned: identity → proof → settlement → governance.
3. **Release checklist is machine-validated in CI** and includes measurable command-level gates.
4. **Provenance manifest covers v2.6 schemas/examples/release assets** and is reproducible for same commit/tag.
5. **Governance evidence packet schema is versioned** with at least one canonical valid example.
6. **Backend exposes deterministic seed-level proof detail endpoint** with tests covering happy path and missing-data path.
7. **Indexer remains idempotent and reorg-safe** after proof detail projection updates.
8. **Dashboard can surface proof completeness and unknown states** without hard failure when backend returns empty data.
9. **Unified runbook exists** with explicit migration notes, provenance checks, and rollback decision points.

## Section 5: Risks / unknowns / assumptions

### Risks
- **Event completeness risk**: current ABI/event mapping may not expose all fields needed for rich seed-level proof diagnostics.
- **Data normalization risk**: adding proof detail reads may require careful handling of `BYTEA` IDs and hex encoding consistency.
- **Operational drift risk**: if runbook commands diverge from CI scripts, operators may pass local checks but fail release verification.
- **Dashboard contract risk**: absent automated UI checks, backend response shape changes can silently degrade operator visibility.

### Unknowns
- Which network(s) are authoritative for RC validation runs (single testnet vs multiple deployments).
- Whether governance adjudication evidence must be signed by single operator, multisig, or council quorum for RC acceptance.
- Whether seed-level proof completeness should include strict timing SLOs in this RC or remain informational only.

### Assumptions
- v2.6 remains a **proof hardening** milestone (no architecture rewrite).
- FastAPI + Postgres and Solidity remain the implementation stacks.
- Changes should land as **small, implementation-ordered PRs**, with release engineering first.
